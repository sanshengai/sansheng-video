# Muse：把导演意图交给实际生成入口

用于通过 Muse 编排生成、选片与剪辑的任务；补充既有 [生成镜头](generated-shots.md)，不另设总流程。下面是自然语言交接模板，不是 Muse API schema，也不保证当前入口支持多参考、首尾帧、分轨、指定时长或分辨率。先核对实际工具能力与返回，再使用相应字段。

按阶段读：规划全片交接 → 「两层交接」「参考图按用途声明」「可复制的镜头卡」；把镜头卡写成真正发出的请求 → [镜头请求模板](shot-request-template.md)；在网页里提交、回收与处理失败 → 「网页执行与回收」；审片与返修 → 「声音和剪辑要跨镜设计」「失败归因与更新」。追求大片感的叙事短片另读 [电影感生成短片](cinematic-generated-film.md)。

## 两层交接，避免只传一句愿望

**影片层给 Muse 编排者**：说明观众、故事变化、观看路径、资产引用、镜头任务、声音与交付。**镜头层给实际生成器**：只保留当前镜头可见的起始状态、动作、摄影、光色和声音。让 Muse 回传实际发送的文本、参考文件及其用途/顺序、参数、工具返回和媒体路径；准备稿不是实际请求证据。无法取得时标记不可核实，不自行补造。

可在既有制作说明中使用以下结构，不要求额外文件或 JSON：

```text
影片目标：谁看；看懂什么变化；风格和不可改变的用户要求。
观看路径：先在哪里，看见谁，发生什么，如何进入下一空间，怎样收束。
参考资产：文件名/可追溯标识 + 用途 + 适用镜头 + 可变/不可变内容。
优先级：明确冲突时采用哪项；用户决定优先，已核实事实不能被示例图覆盖。
镜头列表：每镜使用下方镜头卡。不要把生产编号生成进画面。
声音：对白来源与时序、全片音乐段落、各场环境/动作声及避让关系。
交付：实际可提供的原片/合轨或分轨、实际请求与结果、选片区间、成片规格。
执行范围：先做能检验关键不确定处的代表镜，审后只改受影响项；已授权常规执行不重问。
```

## 参考图按用途声明

- **身份参考**解决是谁及外观，不自动锁定该镜站位、构图和道具。
- **服装/道具参考**解决外观与数量；**场景参考**解决空间、时代、材质和光线。
- **本镜首帧**解决 0 秒人物/物件关系与摄影起点。复杂动作先审首帧是否真的允许动作发生，再请求运动。不是每镜必须新画图；已有合适帧可复用。
- **上一镜末帧**可供邻接参考，但只有当前工具真实支持的方式才使用，不把“引用末帧”写成绝对连续保证。
- **分镜拼板**供人审构图和节奏；未经验证不把多格图直接当单镜首帧，也不假定上传多张图就有角色/场景绑定。

参考优先级因项目而定。例如事实/用户设定 → 身份与场景锁 → 本镜构图 → 摄影动作。发现图文矛盾先解决，不能靠末尾追加“严格一致”抵消。保留可识别的资产引用；“照刚才风格继续”在新会话里没有可追溯对象。

## 可复制的镜头卡

```text
镜头用途：本镜必须让观众看到的一个叙事变化。
实际输入：参考文件、用途、顺序；本入口支持的画幅、时长和声音方式。
0 秒状态：场景/时间/光线；前中后景；人物全身/手脚位置；物件归属与支撑。
动作过程：起点 → 关键变化 → 结果。需要时划分时间窗，动作负荷与总时长相称。
摄影：起始景别/高度/方向 → 有动机的移动轨迹 → 结束构图；说明稳定程度与速度。
结束状态：人物位置、朝向、物件归属、动作是否完成；留下剪点所需可用时间。
接下一镜：下一镜从哪里/什么状态开始，靠动作、视线、空间或声音怎样接。
声音：当前空间环境；动作落点；需要/不需要对白；与全片音乐的关系。
验收：本镜可观察的成功条件和主要错误；不列与当前内容无关的长串禁词。
```

时码是导演意图，不是工具必定逐秒执行的保证。简单镜头用起点、动作、终点即可；复杂运动优先分清主要摄影路径，不把推、拉、摇、旋转、穿越全部塞进一镜。肯定式可见描述通常更便于沟通，但没有证据证明所有否定词失效或英文必然优于中文。

例：集市空间建立镜，前景摊位、中央行人、后方桥和船分别有可读活动；相机缓慢向前，主角走到摊前停下。下一镜从停步后看向货物开始，而不是又从街口重走。宏观景别因此承担位置关系，细节镜承担注意力变化。

## 结构化镜头请求

镜头卡是给人审的；真正发给生成器的请求由「全片锁」加「本镜内容」按固定字段机械拼成。字段、顺序、写法规则、发送前自查、返修纪律和批量拼装脚本见 [镜头请求模板](shot-request-template.md)。下面只补 Muse 特有的要点：

- 一个 Muse 对话开头先发项目说明（模板里的 8 项），再发本批请求；请求正文整段原样作为提示词，让 Muse 不改写、不合并，并在清单里回传实际发送的文本。
- Muse 的「记忆」功能可能把其他项目的设定混进来，所以每条请求都写完整的锁，不依赖「照上一条」。
- 首帧构图图只画 0 秒时已经在场的人。后面才登场的角色如果提前画进首帧，视频会再补画一个人（实测出现过三个人同框）。返工方法是重画首帧，或者改附人物和场景参考图，不再附首帧。

## Agent 编排：流水线就是记忆

生成模型不记得上一条做过什么，连贯性靠 Agent 维护的文件和关卡来保证，不能指望模型自己记住。

- **固定目录**：镜头表（唯一真源）、`参考图/`、`首帧/`、`请求/`、`回传/`（所有原始生成）、`选用/`（通过审片的片段）、生产日志。只有 `选用/` 里的片段进剪辑。参考图和首帧一旦用过就不再改名、不覆盖；新版本存成新文件，旧版本移到弃用子目录。实测踩过的坑：同一镜头新旧两张原图同名排序，脚本先处理了旧图，新图被跳过，旧图又被用上。
- **先锁资产再写请求**：角色、场景、道具的参考图都由作者认可、标为锁定之后，才写生成用的请求。角色锁定前先做一次压力测试：同一个角色在不同景别、不同光线、和其他角色同框各出一张静图，长相和服装都稳定，才算锁定。
- **生产日志**：每次生成记一行，包括镜号、请求版本、改了什么、结果和判定（格式见 [镜头请求模板 · 返修纪律](shot-request-template.md#返修纪律)）。对话编号写进日志，方便回到原对话下载。
- **视觉验收交给一次性子 Agent**：每镜抽 0.5 秒、5 秒、9.5 秒三帧拼成一张小图。子 Agent 对照镜头表逐镜检查人数、造型、动作、机位和画风，只回传文字清单，判定写成「可用 / 取前 N 秒 / 重做」。主对话只看结论和少数关键图，图片不进入主对话的历史。这一条是本项目的做法，公开资料里没有见到「第二个模型看成片」的实现。
- **关卡不跳**：剧情因果审查、静图版、动态画风小样都要作者确认，然后才批量生成（见 [电影感生成短片](cinematic-generated-film.md#3-制作顺序每道关卡过了才花下一笔额度)）。Agent 可以自主做的，是关卡之间的常规生成、下载、抽检和重抽。

## 网页执行与回收

以下来自使用 Muse 网页版的实测（2026-10），属于观察到的现象，不是 Muse 的能力承诺。

- **认准产品**：本页的 Muse 指 Meta 的 Muse（智能体应用 muse.ai，视频由 Meta Superintelligence Labs 的 Muse Video 生成；2026-07 以预览发布）。HeyGen Muse、Microsoft Muse 与第三方「Muse Video」网站都不是它，它们的经验与产出不记作 Muse 结果。官方只写明发布状态，没有公开单段时长、分辨率、画幅或参考图能力，参数一律以实测为准。
- **官方承认的短板**：发布说明点名「音画同步」与「物理准确的快速运动」仍待改进。快速追逐、翻滚、俯冲改用慢动作与前景、风、布料表现速度；需要卡点的拟音收片后先听，不准就重生成或后期补。
- **入口**：网页版没有公共 API，通过已登录会话的浏览器自动化执行。连接哪一个浏览器实例、哪个账号由本机 profile 提供，不写进本仓。
- **同一账号可以分对话并行**：实测在同一账号、同一浏览器里另开一个后台标签页和新旁聊提交生图，另一个 Agent 的对话照常运行、没有报错；该账号的任务列表里本来也有时间交叠的任务。每个任务开自己的标签页和对话，不在别人的对话里追加，不切换别人的标签页；额度是同一池。
- **多个 Agent 各用一个浏览器实例**：同一个 Chrome 里分标签页仍会互相干扰，因为下载设置（CDP 的 `Browser.setDownloadBehavior` 作用于整个浏览器）、窗口焦点和系统保存对话框都是全浏览器共享的。每个 Agent 用独立的 user-data-dir 和调试端口各开一个专用 Chrome，同一账号各登录一次。
- **发送后确认送达**：同时提交很多对话时，消息可能显示「未确认送达」或「消息发送失败」，地址仍停在新对话。提交后等地址变成具体对话、且没有这两种提示才算发出；失败的页面关掉重发，不要把它当成在生成。
- **生图每条消息最多 4 张**，超出部分要下一条消息再要；图片工具没有画幅参数，提示词写 16:9 实际仍返回 1920×1280（3:2）。需要 16:9 时构图上下留余量，后期裁切。
- **视频规格实测**：不附图时返回 1280×720（16:9）、10 秒、24fps，音轨为单声道 AAC 24kHz，整体响度常在 -34～-18 LUFS，入片前要统一响度；单声道 24kHz 的音质上限有限，配乐是否够用必须听审。
- **参考图会带偏画幅**：附了 3:2 的参考图后，视频返回 1152×768（3:2）。参考图先做成目标画幅（角色图两侧补底色，场景图居中裁切）再上传，并在收片时核实。
- **参考图决定画风与场景**：附角色定妆图后，画风明显向定妆图的质感靠拢，角色锚点稳定；不附场景图时，场景会滑向模型默认（例如北方石屋村庄变成日式木屋、云上草原变成普通丘陵）。角色镜附角色图，场景镜附场景图，并逐张写明用途。
- **没有首帧参数**：视频工具只接受提示词列表（文字与图片条目）、名称、输出目录和续接快照，没有首帧、尾帧、画幅、时长、种子或负面提示参数。图片只是提示条目，彼此没有角色区分。实测参考图的构图会压过文字里的 FIRST FRAME 描述（例如要求井口俯视，返回参考图那样的庭院全景）。需要控制开场构图时，先用生图做本镜构图图（附角色与场景参考），再作为该镜唯一的图片传入。实测这样 0 秒画面与构图图基本一致，画风也跟着构图图走；运动过程中仍可能推近或加入多余物件，剪辑时取动作正确的一段。
- **固定机位不可靠**：即使写明 locked-off、no push-in，仍有镜头自行推近成特写；收片时把机位当作必检项，宁可在剪辑里取前段或重生成。
- **运镜幅度会过头**：写「very slow descending crane」的俯瞰镜头一路降到院子特写。需要保持高度时写明「全程保持高空、整片村子始终在画面里」和结束构图。
- **ZIP 下载**：点聊天里的 ZIP 卡片会先打开预览面板，再点面板里的「下载」按钮才会真正下载；自动化时监听下载事件并保存到项目目录，不依赖浏览器默认下载目录。卡片可能在打包写完之前就出现，下载后先校验压缩包（0 字节或校验失败就稍后重下），并与回复里给出的哈希核对。
- **参考图不要补纯色边**：把 3:2 的角色定妆图两侧补纯色凑成 16:9 再上传，色块会被画进输出两侧。角色参考改为单人、单视角、自然背景、原生 16:9 的图；补边不得已时，用场景延展而不是纯色。
- **一个对话只放少量镜头**：实测对话上下文过长时，整批视频生成报错，且没有任何文件交付。每个对话建议 3～4 镜；需要补拍就开新的短对话，附上必要的锁句和首帧，不靠“照刚才的继续”。
- **要求打包回传**：请 Muse 把原片与清单打成压缩包交付，清单写每条文件名、实际发出的请求全文、参考图及用途和顺序。本地按哈希导入，保留原包，拒绝覆盖内容不同的同名文件。
- **失败照实记录**：内部错误、上传被拒或无文件交付时，保存回复原文与时间，不自动循环重试；确认不是请求本身的问题后，在新的短对话里重试一次。额度显示和剩余词元不能换算成可生成条数。
- **收片先量实物**：实测宽高、时长、帧率与是否有音轨；横屏请求曾返回 3:2 画幅，需按全片选定的交付画幅处理，不靠提示词保证比例。
- **返修上限**：每镜首次加最多 2 次返修；每次只改一处并写明缺陷秒点，新旧版本并排比较，到上限选缺陷最少的一版并记下剩余问题。

## 声音和剪辑要跨镜设计

分别声明环境、关键动作、对白和音乐意图，实际返回可能只有合轨。独立短片各带音乐不等于全片音乐连续；先听原声，再决定保留、衔接或用统一配乐补足，避免两层音乐互相冲突。不把作者后配的声音归为 Muse 原生能力。音轨检测和响度统计不能代替听审。

审镜头时连看前后接点：动作有没有重新开始，人物与物件是否瞬移，光线、方向与景别是否跳变。检查时间窗非零、无无意重叠/空洞；“第一视角”不能同时要求完整看到观察者全身。查非预期字幕、Logo、水印，不禁用用户正式品牌或教学字幕。

## 失败归因与更新

实际文件 → 实际输入 → 任务意图依次核对。区分素材生成缺陷、参考图冲突、请求转发遗漏、编辑错误和服务拒绝。一次只改与缺陷相关的变量，记录改前/改后与结果；连续不收敛时重新设计可成立的镜头，不无限扩写提示词。明确安全/内容拒绝时保留原始原因，不换词绕过；原因不明不猜具体触发点。

一次成功不升级为普遍保证；记录采用范围、反例和未验项。Muse 自检与其他 Agent 复核有不同职责，但都不能代替最终媒体、相邻剪辑和真实听审。并行用于独立镜头，依赖前镜末态的镜头先解决输入依赖，不把更多并行等同于更好的连续性。
